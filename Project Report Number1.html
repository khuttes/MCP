Executive summary

Helpyard is a local workstation dashboard built as a single HTML page paired with a Windows PowerShell HTTP bridge. Its purpose is to bring system monitoring, project discovery, process/service controls, a command runner, local Ollama chat, and configuration into one browser interface.

The previously discovered parser and Ollama response-shape defects were fixed and rechecked.
Release decision: suitable for controlled local evaluation, not public internet exposure. The bridge can execute commands and control Windows. Firefox was unavailable in the environment; full browser coverage, complete threat-model hardening, and a mock-backed public demo remain outstanding.

1. Project purpose, scope, and user value

Purpose

Helpyard consolidates common workstation and developer operations in a navigable browser dashboard. The interface is intentionally a regular HTML document; system-level operations are delegated to a separate local PowerShell process because a browser page cannot safely or directly control Windows.

Intended audience and use cases

  • A Windows developer who wants a quick view of CPU, memory, uptime, disks, processes, and services.
  • A user who wants to browse a lightweight list of likely project folders and Git repositories.
  • A local-AI user who wants to select an installed Ollama model and chat without sending that chat to a cloud provider.
  • An operator who needs a browser UI for a PowerShell session, a small set of Windows actions, and service controls.

Design principles visible in the implementation

Local-first

Bridge listener binds to 127.0.0.1; system APIs are served by the same machine. Ollama defaults to loopback.

Single-file UI

HTML, styles, and frontend JavaScript are together in pc-control-dashboard.html; no frontend package manager is required.

Visible controls

Sidebar navigation, connection badge, admin status, confirmation prompts, terminal output, and toast feedback expose operational state.

Incremental product direction

The upgrade plan prioritizes testability and safety before larger project indexing, editing, 3D visuals, or public hosting.

Scope boundary: “Helpyard” is currently a workstation dashboard and a foundation for a developer workspace. Several navigation labels imply future integrations, but not all of them are connected to live backends yet. This report differentiates real behavior from display scaffolding.

2. Architecture and request/data flow

The design has three primary runtime components. The browser owns presentation and user interaction; the PowerShell bridge owns privileged/local operations; optional Ollama handles local inference. An optional cloud chat path calls provider APIs directly from the browser.

5. Bridge/API reference

Connection and authentication

  • Default bridge port: 8787. If busy, the script probes a short configured list of alternatives.
  • Listener prefix: http://127.0.0.1:<port>/.
  • A random 16-byte token is generated at startup when no token parameter is supplied; requests use Authorization: Bearer <token>.
  • Host, remote IP, and non-null origin are checked for local request patterns; protected API routes call the shared authorization function.
  • Ollama base URL defaults to http://127.0.0.1:11434 and can be overridden with a script parameter.

Important implementation gap: the bridge exposes more powerful routes than the UI action registry implies. In particular, /api/run, service changes, PID termination, and MCP process launch are bearer-token protected but are not restricted by an allowlisted command policy. A token holder must be treated as a highly trusted local operator.

6. Security, privacy, and trust boundaries

Existing controls

  • Loopback-only listener prefix limits direct access to the host machine and avoids an intentional LAN bind.
  • Random startup token provides an access check for protected endpoints.
  • Host, client address, and origin checks attempt to limit requests to local browser contexts.
  • Allowlisted system actions include risk/permission/approval metadata, and the server checks approval/admin status for those actions.
  • Claude config writes create a timestamped backup before replacing the file.
  • The README warns not to publish the bridge and recommends loopback serving for the dashboard.

Privacy/data handling

  • Bridge responses include computer name, user name, CPU/memory/disk usage, process names, service inventory, candidate folder paths, and optionally project Git state.
  • Local AI prompts go to the configured local Ollama server by default; the bridge forwards chat content and model name.
  • Cloud chat sends prompt contents and an API key directly from the browser to the selected third-party provider. The cloud key is persisted in the current browser state implementation.
  • No code in the reviewed project establishes a telemetry or analytics system. The absence of observed telemetry is not a substitute for a documented release privacy review.
Safe deployment model: keep the workstation UI/bridge private and local. If sharing a demo publicly, run a separate version with mock data and no routes to local processes, files, services, shell, models, or credentials.

Defects found and corrected during the project work

  1. PowerShell parser failure: malformed token comparison and duplicate authorization helper prevented the bridge script from parsing. Replaced it with one valid check and updated the request handler to use that function.
  2. Local AI empty responses: dashboard read a single JSON object, but the bridge forwarded Ollama's default stream mode. The bridge now requests stream = false and returns the complete response; the UI chat was then verified.
  3. Startup instructions: corrected README and settings guidance so normal startup uses a regular PowerShell session and explains the user-scoped execution-policy bypass.
Not performed: full unit/automation test suite, Windows service mutation tests, reboot/shutdown tests, external network exposure, adversarial security review, Firefox UI run, and public staging deployment.

8. Known limitations and recommendations

Immediate P0 — required before broader local rollout

  1. Contain command execution. Replace general-purpose /api/run with named safe operations, configurable allowlists, and argument schemas. If unrestricted shell access is intentional, make the trusted-user risk explicit and disable it by default.
  2. Unify authorization and policy. Every mutating route (actions, service, process, MCP, config write, command execution) should pass a central policy function with role, target, approval, and audit metadata.
  3. Bound request and execution resource use. Set request body size caps, command duration/timeouts, output size limits, and cancellation behavior. Registry timeout/output labels are metadata today and are not consistently enforced by the routes.
  4. Make errors visible. Remove silent catches in stats/provider flows; add last-success timestamp, error message, retry, and stale-data indication to each panel.
  5. Protect browser state. Handle invalid JSON/corrupt localStorage and browser storage denial. Avoid storing cloud API keys and long-lived bridge credentials unnecessarily; provide an explicit clear/logout flow.
  6. Review discovery and configuration endpoints. Limit project discovery to user-approved roots; restrict Claude config read/write to an intentional UI, with backups and clear confirmation.

P1 — release quality

  • Add regression tests for parser cleanliness, auth, hostile origin, malformed JSON, unknown route, invalid action, approval/admin denial, request limits, and shutdown cleanup.
  • Exercise the supported browser versions on Windows at desktop and narrow viewport sizes; record actual version, result, and screenshot/test evidence.
  • Implement keyboard-visible focus, accessible labels, reduced-motion support, error announcements, responsive table handling, and a deliberate light-theme palette.
  • Distinguish actual tooling discovery from static “Available locally” claims.
  • Add real audit events with timestamps, action, target, caller context, decision and result; avoid recording secrets or full command content where unnecessary.

P2/P3 — product expansion

  • Explicit project folder selection, safe file tree, manifest/language detection, secret-aware excludes, searchable local index, and source-referenced answers.
  • Patch-based editor workflow with diff review, per-file approval, backups, apply/reject/revert and verified test outcomes.
  • Ollama health state, streaming with cancellation, history persistence controls, model settings, and timeouts.
  • Wire MCP server lifecycle UI to bridge routes only after executable allowlisting and isolation are specified.
  • Create a separate public demo mode with synthetic data. Do not tunnel or forward the live local bridge.

10. Installation, startup, and daily-use guide

Prerequisites

  • Windows with Windows PowerShell; regular user permissions for normal read/status use.
  • A current browser. The UI was exercised in the VS Code integrated Chromium browser; other browser products should be tested directly before claiming support.
  • Optional: Python for the simple static HTTP server, or another local static-file host. The bridge itself does not require Node.js.
  • Optional: Ollama reachable at http://127.0.0.1:11434 with at least one pulled model.

Start the bridge

Open a regular PowerShell terminal in the project folder and start the bridge using a process-scoped execution-policy bypass:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bridge.ps1

The bridge prints the listening URL and a generated bearer token. Keep the terminal open while the bridge is in use. Stop it with Ctrl+C.

Serve and open the dashboard

In another terminal, serve this directory on loopback:

python -m http.server 8000 --bind 127.0.0.1

Open http://127.0.0.1:8000/pc-control-dashboard.html in the browser. Serving over localhost provides predictable browser origin/fetch behavior.

Connect and operate

  1. Open Settings from the sidebar.
  2. Enter the bridge URL printed in PowerShell (default port 8787 unless the selected port was changed).
  3. Paste the generated token and select Save & connect. The sidebar should show Connected and the host name.
  4. Use Overview first; navigate to Projects, Processes, Services, or Local AI only as needed. Refresh buttons reload related data.
  5. Use Terminal and action buttons only for commands/actions understood and intentionally authorized. A browser confirmation does not sandbox or neutralize the command.
  6. Clear saved browser data from Settings when finished on a shared profile. Stop the bridge and static server when done.

Final assessment

Helpyard has a compact, understandable architecture and demonstrates useful local workstation workflows. The live system/bridge and local AI path were verified in one Windows Chromium-based environment. Its next success criterion is not more screens; it is consistently enforcing least privilege, surfacing errors accurately, and capturing repeatable cross-browser evidence. Treat the current build as a local prototype until those controls and release gates are completed.
