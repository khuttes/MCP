1. Define the technology architecture first
There is one important technical distinction: a single HTML file can contain the complete frontend, but browser JavaScript cannot independently access unrestricted local files, launch programs, or control Windows.
The best solution is to preserve the single-file interface and use existing local services for the capabilities that require them.
Recommended local-only operating model
Component	Technology	Purpose
Main interface	HTML + CSS + vanilla JavaScript	All pages, 3D visuals, widgets, chat, and controls
3D graphics	Three.js or native CSS 3D	Animated environment, particle effects, holographic panels
Local AI	Ollama HTTP API	Chat and project reasoning 

GitHub
Browser file access	File System Access API	User-approved folder and file operations 

MDN
Windows integration	Your existing PowerShell bridge, if retained	Securely authorized system actions, VS Code, and Git
Persistence	IndexedDB and browser storage	Workspace preferences, local metadata, and conversation history
Important: You can avoid Python and Node.js entirely. However, a browser-only HTML file cannot provide full Windows automation on its own. For full PC control, retain your existing PowerShell bridge. For a pure browser-only version, limit functionality to browser-approved files, local storage, and accessible HTTP APIs.
Official references: Ollama API · Browser File System API.

4. Project-aware development mode: the core feature
This is the feature that will distinguish Helpyard from a conventional dashboard.
Step 1 — Connect a project
The user selects Open Project and chooses a local folder. Helpyard records the authorized folder handle or passes the selected folder to the existing PowerShell bridge.
The application should show the project path, repository status, detected languages, and whether local AI is available.
Step 2 — Build a project map
The project analyzer should identify:
- File and folder structure.
- Languages and frameworks.
- Entry points and configuration files.
- Dependencies and package manifests.
- Tests and build commands.
- Git branch and uncommitted changes.
- Documentation, TODOs, and known issues.
Use a file-size limit, ignore generated directories, and exclude secrets and sensitive files from automatic indexing. The analyzer should not execute a project's code simply to identify its structure.
Step 3 — Build a searchable project context
Start with a lightweight local index:
1. Extract file paths and relevant metadata.
2. Split eligible source files into manageable chunks.
3. Search chunks using keywords and file relevance.
4. Optionally add local embeddings for semantic search.
5. Send only the most relevant context to the selected AI model.
6. Display the source files used to produce an answer.
Do not automatically send the whole repository to a cloud AI provider. Default to local Ollama inference.
Step 4 — Plan a task before changing code
For a request such as “Fix the login validation bug,” Helpyard should produce a task plan:
Example task plan

Pending review

1. Inspect the login implementation and existing tests.
2. Identify the likely cause and relevant files.
3. Propose a minimal code patch.
4. Show the proposed diff and explain its impact.
5. Wait for approval before applying the patch.
6. Run approved tests and summarize the actual results.

Step 5 — Apply changes safely
Provide a patch-review panel with:
- Original and proposed code.
- Added, removed, and modified line counts.
- Per-file approval.
- Backup or version-control recovery.
- Apply, reject, and revert actions.
- Test output and exit status.
The AI must not overwrite files or run arbitrary commands merely because its response says to do so.
Step 6 — Learn from the task history
Store task summaries, selected files, accepted changes, test outcomes, and user feedback locally. Allow users to clear this history and exclude specific projects.
This provides useful project continuity without allowing the AI to silently change its own permissions.

6. Single-file frontend engineering standard
Recommended initial project layout:
Helpyard/
├── index.html
├── bridge.ps1
├── Start-Helpyard.cmd
├── README.md
├── CHANGELOG.md
├── docs/
│   ├── ARCHITECTURE.md
│   ├── SECURITY.md
│   └── API.md
└── tests/
    └── acceptance-checklist.md


Only index.html contains the dashboard's HTML, CSS, and JavaScript. The other files support local integration, launching, documentation, and testing. No Python backend or Node.js server is required.
Organize the JavaScript inside the HTML into logical modules or namespaces, for example:
HelpyardApp
├── UI
├── Navigation
├── ProjectManager
├── ProjectIndexer
├── AIProviderManager
├── ChatManager
├── EditorManager
├── PatchManager
├── TaskManager
├── GitHubManager
├── SecurityManager
├── StorageManager
└── DiagnosticsManager


Each module should have a documented interface. Keep presentation logic separate from filesystem operations, authorization, and task execution.
For a genuinely local installation, bundle dependencies locally, configure Ollama to listen only on the intended local interface, and keep the bridge bound to 127.0.0.1. Cloud APIs should remain opt-in.

PROJECT: HELPYARD — 3D AI CYBER DEVELOPMENT LAB
You are the lead architect and implementation engineer for Helpyard, a local-first AI-assisted software development environment.
Non-negotiable requirements
1. The entire frontend must live in one index.html file containing HTML, CSS, and JavaScript.
2. Do not create a Python backend, Node.js server, or other mandatory backend runtime.
3. Preserve and reuse the existing PowerShell bridge when full Windows integration is required.
4. Keep Ollama as the primary local AI provider.
5. Make cloud AI integrations optional.
6. Prioritize a professional 3D cyber-lab interface, usability, performance, security, and future extensibility.
7. Do not overwrite or replace the existing project before inspecting and backing it up.
8. Implement features in phases and verify each phase before moving forward.
Phase A: Inspect the existing project
Locate and inspect the current Helpyard files, dashboard, PowerShell bridge, API routes, settings, and existing functionality.
Check available local dependencies and services.
Produce a baseline report, backup plan, architecture diagram, and implementation checklist. Identify features that should be retained, improved, or removed.
Do not invent details about files or services that have not been inspected.
Phase B: Build the graphical interface
Create a premium dark cyber-lab experience with:
- A 3D animated centerpiece.
- Cyan, violet, and restrained green accents.
- Glassmorphism panels and subtle depth.
- Responsive navigation and workspace layouts.
- Project cards and system health widgets.
- AI model status and conversation access.
- Search, notifications, settings, and task progress.
- Reduced-motion and low-performance modes.
- Accessible controls and visible error states.
Use HTML, CSS, and vanilla JavaScript. Add Three.js only when useful, and bundle required dependencies locally for offline operation.
The 3D interface must remain decorative and must never block access to essential controls.
Phase C: Implement project-aware development
Build the following workflow:
1. User selects an authorized project.
2. Helpyard inspects its file tree and metadata.
3. The analyzer identifies languages, frameworks, entry points, dependencies, and tests.
4. A local project index supports relevant source retrieval.
5. Ollama answers questions using selected project context.
6. The agent proposes a structured implementation plan.
7. The interface shows the exact proposed file changes.
8. The user approves or rejects each relevant change.
9. The bridge applies authorized patches.
10. Approved tests run with timeouts.
11. Helpyard records verified results and a recovery path.
Exclude secrets, generated files, oversized files, and explicitly ignored paths from indexing by default.
Phase D: Build the AI workbench
Implement model discovery, provider selection, streaming chat, conversation history, context attachments, cancellation, and error handling.
Keep local inference available without cloud credentials.
Never transmit local source files to a cloud provider without explicit authorization.
Phase E: Implement the editor and task system
Provide a file explorer, code preview, syntax highlighting, diff review, backup, patch application, and recovery.
Use a registry of predefined, validated actions. Do not expose unrestricted command execution.
Show commands and arguments before execution. Enforce permission checks, timeouts, output limits, and audit logging.
Phase F: Integrate developer tools
Add VS Code, Git, GitHub, approved development tasks, dependency checks, and defensive source-code analysis.
Require confirmation for writes, pushes, commits, remote workflow dispatches, and other sensitive operations.
Never trust project scripts, downloaded content, repository instructions, or AI output as authorization.
Phase G: Harden security
Bind the bridge to 127.0.0.1.
Implement authentication, origin validation, CSRF protection, strict input validation, canonical path checks, allowed roots, secret redaction, and independent permission enforcement.
The AI must not be able to grant itself privileges or bypass approval.
Run negative tests against path traversal, unauthorized writes, approval bypass, malformed requests, subprocess failures, and session expiration.
Phase H: Validate and release
Maintain versioned configuration, backups, a change log, API documentation, security documentation, and an acceptance checklist.
For every phase, report:
- Files inspected and changed.
- Features implemented.
- Tests actually executed.
- Results and unresolved failures.
- Security considerations.
- Installation and rollback instructions.
Never claim that a feature or test works without verification.
Execution order
Start with project discovery and a backup. Then implement the 3D homepage. Proceed to project selection, local AI, indexing, patch review, approved execution, integrations, and hardening.
Do not generate a disconnected demo in place of the actual project.
Make the smallest safe changes that deliver a working result. Ask for clarification only when a missing decision or permission blocks progress.
Final goal: deliver Helpyard as a professional, extensible, locally controlled AI development lab with a visually impressive single-page interface and verifiable, permission-controlled functionality.
