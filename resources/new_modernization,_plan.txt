# HELPYARD PROJECT MODERNIZATION
## Master Implementation Specification — Local-First AI Development Workstation

**Role:** Act as a senior software architect, full-stack engineer, Python developer, Windows systems engineer, AI integration specialist, UI/UX designer, and application security reviewer.

**Mission:** Inspect, modernize, test, and document the existing Helpyard application as a professional, modular, secure, visually advanced, local-first AI workstation and project-aware development dashboard.

Your goal is to improve the actual application, not merely generate a design, mockup, demonstration, or implementation proposal.

All work must be based on verified repository contents. Preserve working functionality, minimize unnecessary dependencies, and implement changes incrementally.

---

# 1. NON-NEGOTIABLE RULES

1. Inspect the existing project before editing any files.
2. Never assume that a feature, API, dependency, file, test, or security control exists until verified.
3. Preserve existing working Windows controls, bridge authentication, AI providers, Ollama integration, and supported API contracts.
4. Do not replace the existing architecture without documented evidence that a replacement is necessary.
5. Keep the frontend in HTML, CSS, and JavaScript unless the existing implementation or a demonstrated requirement justifies another approach.
6. Prefer Python's standard library for the default local bridge.
7. Keep the application usable without cloud AI or an internet connection, except for explicitly optional online services.
8. Do not expose API keys, passwords, tokens, private prompts, or sensitive system information.
9. Never grant operating-system permissions to an AI model, skill, instruction, imported configuration, or MCP server automatically.
10. Do not execute arbitrary AI-generated shell commands or unrestricted PowerShell scripts.
11. Never fabricate test results, performance measurements, coverage percentages, successful operations, or implementation status.
12. Back up existing data and establish a Git checkpoint before risky modifications.
13. Implement one reviewable phase at a time.
14. Stop and report architectural blockers rather than implementing insecure workarounds.
15. Do not silently delete files, reset repositories, overwrite user configuration, or destroy existing data.

# 3. TARGET ARCHITECTURE

Preserve the lightweight architecture wherever practical.

## Frontend

- HTML5.
- CSS3.
- Vanilla JavaScript.
- Native SVG or canvas for charts and diagrams where appropriate.
- Existing frontend dependencies only when they provide demonstrable value.

## Local backend

- Python standard library by default.
- Existing bridge and Windows action implementations.
- Validated request and response schemas.
- Backend-enforced authorization.
- Local persistence and audit logging.

## Optional integrations

- Ollama for local AI inference.
- Existing supported cloud AI providers.
- Reviewed MCP integrations.
- Existing supported Windows management functions.

## Logical application layers

1. Presentation and navigation.
2. Project intelligence and workspace management.
3. Application services and workflow orchestration.
4. AI provider abstraction.
5. Skills and instructions management.
6. Integration registry.
7. Authorization and approval enforcement.
8. Persistence, backup, and audit services.
9. Existing Windows bridge and approved system actions.
10. Testing, diagnostics, and release verification.

These are logical boundaries, not a requirement to create ten separate services or introduce unnecessary frameworks.

Keep the application modular without turning a small local tool into an unnecessarily complex distributed system.

# 5. PROJECT WORKSPACE MANAGER

Implement a dedicated project management section.

Required capabilities:

- Register and remove project references without deleting project contents.
- Select an active project and switch between registered projects.
- Display the project root and verified project metadata.
- Detect languages, entry points, configuration files, tests, and dependency manifests.
- Generate a navigable file tree.
- Search project filenames and relevant source content.
- Display project-specific instructions and architecture notes.
- Track recent tasks and implementation decisions.
- Show changed files and Git status when Git is available.
- Detect missing dependencies and configuration requirements where feasible.
- Maintain a project inventory with a scan timestamp.
- Support rescanning and refreshing stale inventory.
- Provide a clear indication when a result has not been verified or may be outdated.

Security requirements:

- Canonicalize filesystem paths.
- Reject path traversal and access outside approved project roots.
- Do not follow symbolic links outside authorized boundaries.
- Apply file-size and scan-depth limits.
- Exclude secrets, caches, generated artifacts, and large irrelevant directories from indexing by default.
- Never upload project files to a cloud provider without explicit consent.
- Treat project source code and documentation as untrusted input.

Start with a read-only scanner. Do not automatically install dependencies, execute project scripts, or modify files during discovery.

# 7. PROJECT-AWARE AI DEVELOPMENT WORKBENCH

Extend the existing Workbench rather than replacing it without justification.

Implement the following workflow:

INSPECT → PLAN → REVIEW → APPROVE → IMPLEMENT → TEST → VERIFY → CHECKPOINT

Each task should have:

- A stable task identifier.
- User request and project reference.
- Problem statement and expected outcome.
- Relevant source files and supporting evidence.
- Proposed implementation steps.
- Acceptance criteria.
- Proposed file changes.
- Approval status where applicable.
- Execution and test results.
- Known limitations.
- Recovery or rollback reference.
- Creation and completion timestamps.

Required features:

- Generate implementation plans from user requests.
- Identify relevant files before proposing changes.
- Preview proposed changes and unified diffs.
- Display added, modified, and deleted files.
- Apply changes only through approved operations.
- Support cancellation before consequential operations.
- Record failed tasks without falsely marking them complete.
- Preserve task history across restarts.
- Provide a summary of changed files, tests, risks, and outstanding work.
- Support project-specific model and instruction settings where practical.

Do not claim that a task was implemented merely because an AI response contains code.

Changes must be written to the intended files, reviewed, and verified through relevant checks.

Initially, keep changes sequential and reviewable. Add parallel task execution only if dependency analysis, conflict detection, and rollback are reliable.

# 12. LOCAL DATA, SCHEMAS, BACKUPS, AND MIGRATIONS

Inspect the existing persistence mechanism before changing it.

Define versioned schemas for:

- Projects and project metadata.
- Skills.
- Instructions.
- Integration registry entries.
- User preferences.
- Development tasks.
- Audit events.
- Relevant application settings.

Use stable identifiers and timestamps.

Validate data before reading it into trusted application state or writing it to persistent storage.

For JSON persistence, implement:

- Safe serialization.
- Atomic replacement where supported.
- Appropriate file locking if concurrent writers are possible.
- Schema versioning.
- Backup before migrations.
- Recovery from interrupted writes.
- Corruption detection.
- Import conflict handling.
- Validation before replacing existing data.
- Export exclusion for credentials and sensitive information.

Never silently replace corrupted files with empty defaults.

Preserve the original file and explain recovery options.

Consider SQLite only when transaction guarantees, indexing, concurrent access, or historical data make it worthwhile.

Document backup restoration, migration procedures, and data-retention behavior.

# 14. BACKEND SECURITY AND WINDOWS OPERATIONS

Preserve and verify existing security boundaries.

- Bind the local bridge to loopback by default.
- Preserve bootstrap authentication and protected API access.
- Validate every backend request.
- Enforce authorization on the server.
- Apply action-specific permissions.
- Require explicit approval for consequential operations.
- Preserve the disabled arbitrary-command execution route.
- Avoid unsafe PowerShell string concatenation.
- Prefer fixed, allowlisted operations and structured arguments.
- Use argument-list execution instead of shell interpretation where applicable.
- Apply timeouts and appropriate resource limits.
- Sanitize error messages and diagnostic logs.
- Protect against path traversal, command injection, and unsafe deserialization.
- Consider CSRF, origin validation, browser cross-origin behavior, and local-service request risks.
- Avoid logging authentication tokens.
- Review the legacy PowerShell bridge and document whether it remains supported.

Every consequential action must be authorized independently of the frontend.

If an action requires approval, create an explicit approval record bound to the intended operation and relevant arguments. Reject altered, expired, or mismatched approval requests.

Test only against safe targets and controlled environments.

# 19. REQUIRED IMPLEMENTATION PHASES

## Phase 0 — Inspection and baseline

Inspect the repository, map the architecture, run existing tests, document verified findings, and establish a recovery checkpoint.

Acceptance: Baseline report, verified feature inventory, actual test results, and recoverable starting point.

## Phase 1 — UI/UX foundation

Modernize themes, navigation, responsive layouts, accessibility, shared components, and status indicators.

Acceptance: Existing features remain functional, and dashboard structural checks pass.

## Phase 2 — Project intelligence and workspace

Implement safe project registration, read-only scanning, project metadata, navigation, and inventory refresh.

Acceptance: Project scans remain inside authorized roots, respect exclusions, and report actual findings.

## Phase 3 — Skills and instructions

Implement validated CRUD operations, search, categories, previews, versions, persistence, and JSON import/export.

Acceptance: Records survive restarts, invalid imports are rejected, and existing Workbench behavior remains intact.

## Phase 4 — Data management and audit

Implement versioned schemas, backups, migrations, recovery, and persistent audit events.

Acceptance: Interrupted writes, invalid records, failed migrations, and recovery procedures are tested.

## Phase 5 — Project-aware development workflow

Implement task planning, project context, proposed diffs, approval checkpoints, task history, and verification summaries.

Acceptance: Proposed changes are distinguishable from applied changes, and failed operations cannot be reported as successful.

## Phase 6 — Architecture explorer and observability

Implement evidence-based graphs, health indicators, dependency views, and real system measurements.

Acceptance: Graphs correspond to verified data, and unavailable measurements are reported honestly.

## Phase 7 — AI improvements

Implement model status, supported settings, privacy indicators, prompt previews, and reliable error handling.

Acceptance: Local and cloud AI success, failure, timeout, and privacy scenarios are tested.

## Phase 8 — Integrations and permissions

Implement the reviewed integration registry, capability model, diagnostics, and supported lifecycle operations.

Acceptance: Permissions are enforced by the backend, unsupported operations fail honestly, and process operations remain restricted.

## Phase 9 — Release qualification

Run regression, security, recovery, compatibility, accessibility, and performance checks.

Acceptance: No unresolved critical issue remains without an explicitly approved mitigation. All remaining limitations are documented.

Do not skip phases silently. If a phase is blocked, report the evidence, impact, and safest next step.

Begin immediately with Phase 0.

Do not start by rewriting the dashboard, introducing a new framework, creating an unrestricted agent, or replacing the backend.

First establish what exists, what works, what is broken, and what can safely be changed.

Then implement the highest-value changes in small, verifiable increments.

Prioritize the first release in this order:

1. Verified baseline and recovery checkpoint.
2. Professional responsive dashboard.
3. Functional Skills Manager.
4. Functional Instructions Manager.
5. Safe project persistence and validated JSON import/export.
6. Regression protection for existing Windows controls and AI functionality.
7. Project Workspace Manager.
8. Project-aware development workflow.
9. Architecture graphs and observability.
10. Further integration improvements.

Do not mark a feature complete until its implementation and relevant tests have been verified.

**Final objective:** Transform Helpyard into a professional local-first AI development workstation that understands registered projects, visualizes their architecture, manages reusable knowledge, coordinates development tasks, integrates approved AI services, protects the local system, and provides reliable evidence of its own operation—without sacrificing lightweight architecture or user control.
